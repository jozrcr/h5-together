## In short

- **The host chooses.** On the game setup screen or in the waiting room, the host presses **F2** (or clicks our **"Rules..."** button at the right of the waiting room's title) and gets a panel with the game mode, ToE's start bonuses, 15 of MMH5.5's switches and "MMH5.5 scripts on random maps", each with a one-line explanation, in French or English. Gold = changed from the host's own MMH5.5 file. **OK** saves the choice in `open-homm5.ini` `[rules]` (it is there next time); **MMH5.5's file** puts every value back to the file's.
- **Nothing changes unless the host changes something:** the panel starts from the host's `scripts/H55-Settings.lua` as installed (read at run time, so a group's own settings pak still counts).
- **The other players see the host's rules** in the waiting room (F2 or "Rules...", read only), and everyone sees the rules of the running game with F2 on the adventure map.
- **Every PC uses the same values:** they travel inside the game's own start message, so it works on **any map**, random or hand-made.
- **A PC without the add-on (or with it off) cannot start on other rules:** the host then sends no rules, and every PC uses its own MMH5.5 file, exactly as without the add-on. The host's log and panel say so ("Without open-homm5: Robot-client").
- **The rules check:** every PC's add-on tells the host a fingerprint of its MMH5.5 files (`H55-Settings.lua` and the stats paks). The host's log and panel name a player whose files differ, and that player's panel says so too.
- **Saves keep the rules the game started with:** the scripts read the file once, at the map's start, and a save keeps their values (robot-checked in single player).
- **MMH5.5's scripts on a random map straight from the game's generator, in a multiplayer game:** they need a map script, which such a map does not have. With RC19d they do not run there (then the other switches change nothing); RC19k's `55u.dll` runs them anyway. The rule **"MMH5.5 scripts on random maps"** (`map_scripts`) now decides it for every PC of the game; its default is what the installed MMH5.5 does (RC19d: off, RC19k: on). Hand-made maps and random maps saved with a map script (MMH5.5's Mapmixer or the editor: all of the owner's saved maps but the `MMH55_RMG_Map_...` ones) always run them, and so does single player.

## Step 2: game mode and start bonuses (built 2026-11-01)

**What MMH5.5 does** ([lobby-audio-classes.md](lobby-audio-classes.md), item 2). Each lobby row has bonus arrows (ToE's start bonus: random, minor artifact, gold, resources). The game hands the bonus out when the map starts. Then MMH5.5's start script, `scripts/H55-AdvMap.lua` (`H55_PrepareAdvMap`, the part from `H55_DEBUG = {102,"StartingBonus"` to `{103,"StartingArmies"`, dofile'd by `H55-Core.lua` on every PC), looks at each human's gold, resources and first hero's artifacts, recognises the bonus, **takes it back**, gives each human's first hero a random minor artifact of its own (`H55_ArtifactStartBonus`; its creature bonus is commented out), and makes one **game mode** of the humans' picks: any artifact = Default, else any gold = Savage, else any resources = Nightmare. Savage and Nightmare stop the AI heroes from fleeing (Nightmare: also unlootable) and team the computer players against the humans (`H55_TeamHumansvsAI`, or `H55_TeamAI` with `H55_NoAutoTeamHumans = 1`). Scenarios, campaigns and games without computer players get Default; "casual" is decided elsewhere (`H55_UpdateGameMode`) and is left alone.

**The two rules** (group "Game mode and start bonuses", first in the panel; `[rules]` keys; not in `H55-Settings.lua`, so "0" is each PC's default):

| `[rules]` key | Values | Default |
|---|---|---|
| `game_mode` | 0 = the bonus arrows (MMH5.5's way), 1 Default, 2 Savage, 3 Nightmare, 4 Random (one of the three, drawn in the script with the game's shared random numbers, `random(3)+1`) | 0 |
| `toe_bonuses` | 1 = each human keeps the ToE bonus picked with the arrows, and MMH5.5's start artifact is not given | 0 |

With `toe_bonuses=1` and `game_mode=0`, the mode is Default (the arrows now choose bonuses). **Why MMH5.5's start artifact is not given with the ToE bonuses:** it is exactly ToE's "minor artifact" bonus given to everyone; on top of a ToE bonus, an artifact picker would get two. With `toe_bonuses=0` and a mode, MMH5.5 still takes the bonus back and gives its artifact (only the mode is the host's).

**The served script** (`PatchStartScript`, every PC, when a start rule is not MMH5.5's way). Three edits inside the "StartingBonus" part, each place found **exactly once** (and in this order), else the file is served as it is and the log says why (`REFUSED`):
1. after `local amountai = table.containsamount(H55_PlayerStatus,1);`: a line `local OH55_KeepToEBonus, OH55_Mode = <toe>, <mode>; -- open-homm5: ...`;
2. the humans' loop `if H55_MapType ~= "Campaign" then` gets `and OH55_KeepToEBonus ~= 1` (the whole take-back and MMH5.5's artifact are skipped);
3. before `if H55_MapType == "Scenario" then` (the mode's decision): one line that sets MMH5.5's three "somebody chose" flags from `OH55_Mode`. MMH5.5's own decision code then runs unchanged: its prints, the AI heroes that never flee, the teams.

The checks also require the three flags to be locals of the part before the AI count, the loop to contain the take-back (`SetPlayerResource(i,6,`, `RemoveArtefact(heroes[0]`, `H55_ArtifactStartBonus(heroes[0]);`), and the decision to read the three flags. Each new line takes its neighbour's indent and line end (the file mixes CRLF and LF). Unit-tested on a text of ours in the file's layout (`TestStartScript`: the edits, nothing else changes, refusals); checked on the real RC19d and RC19k files in the scratchpad (never committed): both patch, and their "StartingBonus" parts are **identical** (hash `da18d7b6`), so an RC19d and an RC19k PC can play together on these rules. With `[rules] trace=1`, one more line before the next part prints each player's start resources and minor artifacts to the console (testing only).

**Every PC the same:**
- the rules travel in the start message with the others (protocol 2: `OHR2`, `L2`, now 3 with `map_scripts`; a PC with an older protocol counts as "without the add-on");
- each client's hello also sends the hash of its "StartingBonus" part (mark `'A'`). The host uses the start rules only when its own part takes our edits and every human client sent the same hash; otherwise it sends them as "0" (MMH5.5's way, the arrows choose the mode), logs `rules: START: the game mode and ToE start bonuses stay MMH5.5's way ...`, and both panels say why (the lobby text's flag `kNoStart`);
- a PC without the add-on: no rules at all, MMH5.5's way everywhere (step 1's rule).

**The lobby's tooltips** (`host_rules_bonus.cpp`). The game reads each text file once per session, and each lobby row copies the four bonus tooltips when it is made (`0x00714f00`), before a joining client knows the host's rules, so serving other text files cannot follow the rules. Instead, every 0.5 s, the lobby logic's update rewrites each row's own copies: the row (`NUI::CMPWaitItem`, vftable `0x00e39ce8`) keeps at `+0x108` a vector of five `hash_map<int, wstring>` (0x18 bytes each); the fourth (`+0x48`) holds the bonus tooltips by bonus number; `0x0040e960` (`wstring::assign(first, last)`) puts our text in, and the icon (`+0x9c`) gets the one of the row's bonus (`+0x84`) through its vtable slot `0x68`, exactly as the row's refresh `0x00713fe0` does. Our texts (English or French, the panel's language): ToE's bonus (e.g. "Start bonus: gold. 500 to 1000 more gold at the start.") and "Game mode: Savage (the host's game rules)"; with only a mode, "No start bonus to choose: MMH5.5 gives every human player's first hero a random minor artifact." MMH5.5's texts come back when the rules go back to MMH5.5's way (or a player without the add-on joins). **Gaps:** the icons stay MMH5.5's mode pictures (a fist and a burning town for gold...): the game loads them once too, and swapping them would need the icon's texture list (not studied; MMH5.5's pak still has three of ToE's icons as `Gold_ret`, `RandomArtifact_ret`, `Random_ret`); the tooltips were set without an error in every run, but the robot cannot hover, so nobody has seen them on screen yet.

**Found on the way:** the lobby's arrow kinds are a row's pending request type `+0xc4`: 1 state, 2 team, 3 faction, **4 hero** (`hero_change_*`, `0x007138e0`/`0x00713900`), **5 start bonus** (`bonus_change_*`, `0x00713920`/`0x00713940`). The host's handler asks the game setup (`NWorld::CPlayersStartInfo`, vtable `0x00e92744`) first: `+0x3c`/`+0x40` for a hero, `+0x44`/`+0x48` for a bonus. The robot's `arrow` step has `<row> bonus left|right` and `<row> hero left|right`. ToE's resources bonus is 3 to 6 of one random resource (seen: +4 sulfur, +6 mercury, +5 gems, +4 mercury); gold is +500 to +1000 (seen: +900, +800).

## How the choice reaches every PC (research, 2026-11-01)

| Channel | Direction, when | Verdict |
|---|---|---|
| **Waiting-room requests** (`NUI::CMPWaitChangeRequest`: a row, a type, a byte; the faction mod's hello) | client → host, in the lobby | **Used for the hello.** The host's handler (`0x0071f3d0`) ignores types it does not know. A hello is type `0x4f52` ('OR') with the protocol version in the byte; five more carry 32-bit hashes, the mark in the type's top byte ('N', 'S', 'X', then 'A' the start script and 'C' the class table) and 24 bits, the top 8 bits in the byte. Sent every 4 s, one per frame on the first row's free request slot, as the faction mod does. |
| **A UI command to one PC** (the host's transport, logic `+0x10`, slot 8: "SendDirect", as the game's own `0x0071e7b0` sends each PC its arrow locks) | host → client, in the lobby | **Used for the lobby display.** A client's handler (`0x0071ef10`) gives an `IMPWaitUICommand` to a row only when the row exists, so a command for row `0x4f52xxxx` is ignored by a client without the mod. The **hero-name command** (`CMPWaitChangeHeroNameUICommand`, it holds a string) left the host ("SendDirect: ... to 1" in the console) but **never reached the client**: the game does not send that class over the network. The **lock-buttons command** (`CMPWaitLockButtonsUICommand`, `0x007111d0`: a row and a 32-bit mask) does arrive. So the text goes 4 bytes at a time: rows `0x4f52 << 16 | seq << 8 | index`, piece 0 = the length (`LobbyPieces`, `LobbyAssembler`). The text is short: `L1|<flags>|0,1,5,1,1,1,2,0,1,1,0,1,0,1,1` (11 pieces). |
| **The start message** `NMP::CMPStart` (vftable `0x00e3a4dc`; serializer slot 3 `0x007208a0`) | host → every client, at the start | **Used: the binding channel.** The game's binary saver (`CStructureSaver`) writes numbered chunks; its reader looks a chunk up by its number (`0x00cb6370`) and skips the others. After the message's own chunk 3, the host writes **chunk `0x4f`**, 512 bytes: `OHR1;governance=0;...;moon_disc=1` (every rule's value), zero-filled. A client without the mod skips it; ours reads it while the message is read (before the world is made). The host's own game runs from the same message object, not a copy (`0x0071feb0` sends it, then hands it to its own handler). |
| The game info the host advertises (`NUI::CGameData`, the LAN list's 826-byte answer) | host → PCs looking for games | Not used: it is for finding games (and GameRanger has its own), not for the PCs already in the lobby, and it would not reach a PC that joined by address. |
| The co-op guard's ignored checksum messages ([coop-timing-guard.md](coop-timing-guard.md)) | every PC → every PC, after the first segment | **Too late.** The scripts read `H55-Settings.lua` about 0.3 s after the game starts (robot: the start at 47.8 s, the read at 48.2 s), before the first segment. |

**Every PC applies the identical rules before the scripts read the file:**
1. The host decides when it starts (`0x0071feb0`, the call at `0x007200da`): every human player's PC (slot state 2, not the host's) must have said hello with the same protocol version.
2. A client takes the chunk's values when it reads the start message; the host takes its own.
3. When the world starts (`NUI::CRunMPGame`, slot 7 `0x0071d660`), those values become **this game's rules**. A single-player start (`NUI::CStartSingleAdventureMap`, slot 7 `0x007e1030`) drops them: single player always uses the file.
4. When the map's scripts read `scripts/H55-Settings.lua` (`advmap-startup.lua` → `advmap-common.lua` → `H55-Core.lua`, every PC), the file hook serves it with those values.

**A PC without the mod**, or with `[rules] enabled=0`, or with another protocol version, says no hello (or another version), so the host sends no chunk, and every PC uses its own file, as without the mod. The host's log has `rules: START: Robot-client without open-homm5's rules: every PC uses its own H55-Settings.lua`, its panel the same warning, and our lobby button a red "!".

**Versions.** The carried text starts with `OHR4` (the lobby's with `L4`; step 1 used `OHR1`, `L1`, step 2 `OHR2`, `L2`, `map_scripts` `OHR3`, `L3`); a PC refuses a text with an unknown key or a bad value (`Decode`), and the hello carries `kProtocol` (2 since step 2, 3 since `map_scripts`, 4 since `class_skills`). A new rule = a new protocol version, so an older PC is treated as "without the mod" and nobody plays on rules it cannot apply.

## How each PC applies them

The game's "open file" (`NVFS::CWinVFS` slot 7, `0x009e0020`, stacked with the other mods' wraps) is wrapped. When the scripts open `scripts/H55-Settings.lua` and this game has the host's rules:
- each plain assignment `NAME = number` of a rule's variable, at the start of a line (or after a `;` on it), outside `--` comments and `--[[ ]]` blocks, gets the new number: **only the number's characters change** (unit test: every other byte is the same);
- a variable the file does not have, or that it also sets with an expression, gets a line at the end (`H55_X = v; -- open-homm5: the host's rules`): Lua's last assignment wins;
- with the file's own values, the served file is the same bytes as the file;
- the log has the values, what changed and the served file's hash, e.g. `rules: the scripts read scripts/H55-Settings.lua: served with the host's rules (governance 1->0, ai_cheat 4->0, mixed_stacks 1->0; ...); 8206 -> 8206 bytes, hash a07c5c34`. Every PC of a game should log the same hash.

The host sends the value of **every** rule (its file's, with its choices), not only its changes, so a PC whose file has other values for these switches still plays on the host's. The rest of the file must be the same everywhere: that is the check below.

Never committed: the file itself (MMH5.5's text). The unit test uses a text of ours in the file's format.

## The rules check (C.1 way 2)

Each PC hashes (FNV-1a, 32 bits), once per session, when the lobby needs it:
- its `H55-Settings.lua` as installed, **without the rules' values** ('N': only that part must match, the host's values replace the rest), and whole ('S');
- MMH5.5's stats files the way `55u.dll` looks for them (its own list: `..\UserMODs\MMH55-CustomStats.h5u`, `..\data\MMH55-Stats.pak`, `MMH55-Stats1..9.pak`): the names and bytes of those that exist ('X').

The host compares them with its own: `rules: CHECK: Robot-client (PC 1) has another MMH5.5's stats files than the host (...): the game may not stay in step`. The panel lists the players whose files differ, the button gets a red "!", and the client's own panel says "Your MMH5.5 files differ from the host's". This only warns; the game still starts.

Not done: the same check in the co-op hello once the game runs (the co-op guard's message carries one number; a second message would do, see "Later").

## Saves

**A loaded game keeps the rules it was started with.** MMH5.5's scripts read `H55-Settings.lua` once, when a map starts; a save keeps the scripts' variables and threads. Robot check (RC19k, single player, `[rules] trace=1`, which logs every script file the game opens): a new game on A1M4 opened `advmap-startup.lua`, `H55-Core.lua`, `H55-Settings.lua` and the rest (run `20261101-203522`); loading its day-2 autosave (`Sauvegarde auto 3`, run `20261101-203603`) opened **no script file at all**, printed no `H55 Lua Library and Tables initialized`, and MMH5.5's scripts went on (`H55 Daily Event 2 Finished`, `H55 Player Configuration: ...` on each new day). So whatever the host's panel says when a save is loaded, the game goes on with the values it started with, on every PC (each PC loads its own copy of the save, made from the same world). A multiplayer load was not robot-tested (the robot cannot open the multiplayer load screen yet); it uses the same script engine.

`class_skills` is not in the scripts but in the game's class table, which a save does not hold: the add-on puts it into the saved world itself (one more chunk), see "Step 3", "Saves".

## MMH5.5's scripts on random maps (`map_scripts`, 2026-11-01)

The owner: "Shall we add an option to select if we process through MMH 5.5?" Yes: one more rule in the panel, **"MMH5.5 scripts on random maps"** / **"Scripts MMH5.5 sur les cartes aléatoires"** (`[rules] map_scripts`, group "Random maps"). It is not a line of `H55-Settings.lua`: the add-on applies it itself, on every PC, from the start message like the other rules.

### What makes a map run MMH5.5's scripts

Two places of the game run `scripts/advmap-startup.lua` (which loads `advmap-common.lua` → MMH5.5's `H55-Core.lua`, `H55-Settings.lua`...):

| Where | When | Needs a map script? |
|---|---|---|
| The adventure screen's own script context: `NUI::CAdventureController`'s constructor (`0x006089a0`) → `0x00603b20` | a new game, only where "console script commands" are allowed (`0x006b9de0`; otherwise the log has "Warning: console script commands are not allowed"): **single player** | **No**: it runs `advmap-startup.lua`, `createAdvmapAliases();`, then the map's script file if it has one |
| The world's script host (`NWorld::CWorld` +0x1d0): world slot 128 `0x009941a0` → `0x00992d00`, given the map's `NDb::SScript` by the world's creation `0x00c9fa80` (`FUN_00441d00(&desc->MapScript)`, NULL for `<MapScript/>`) | a new game whose world settings (world slot `0x14`, two bytes) say multiplayer: **LAN and GameRanger games** | **Yes**: `if (map_script == 0) return;` (the `jz` at `0x00992d2a`), then it makes the `advmap` script machine and runs `advmap-startup.lua`, `createAdvmapAliases();` and the map's file (`SScript` +0x44..+0x48, its file name) if the name is not empty |

### How the add-on does it

Our wrap of world slot 128 (`0x00e6280c`, the vtable cell of `NWorld::CWorld`), only while a multiplayer game's world is made (inside `NUI::CRunMPGame` slot 7), and only with the host's rules:
- the map has its own script: nothing changes;
- no map script and `map_scripts=1`: the world gets **an empty script** (a block whose file name, at +0x44..+0x48, is empty). `0x00992d00` then does what it does for a Mapmixer map: it makes the script machine, runs `advmap-startup.lua` and `createAdvmapAliases();`, and skips the map file (empty name). Every PC does the same, from the same start message;
- no map script and `map_scripts=0`: the wrap does not call the slot, which is what the original game does without a map script (`0x00992d00` returns at its `jz` and does nothing else). So "off" also turns RC19k's scripts off on those maps;
- no host's rules in this game (a player without the add-on, `enabled=0`): nothing changes: each PC's MMH5.5 decides, as without the add-on.

**Byte checks** at start-up: the slot holds `0x009941a0`; its code is `8b 89 d0 01 00 00 85 c9 74 05 e9 51 eb ff ff` (the script host at +0x1d0, then a jump to `0x00992d00`); `0x00992d26` is `39 5c 24 34` (the null test); the name read at `0x00992db1` is the game's `8b 44 24 3c 8b 48 48 8b 50 44` or RC19k's jump `e9 <rel> 90 90 8b 50 44` whose target starts with the 18 bytes quoted above (the only reads of the script: its name, +0x44 and +0x48). If any differs, the whole rules mod stays off (no hello: no PC plays on rules it cannot apply); the log says which (`rules: map_scripts: ... (code 110)`). The name read is checked again before an empty script is given (an MMH5.5 that patched later: then no scripts, logged `FAILED`). Log at start-up: `rules: map_scripts: the world's script start is as expected (its name read: the game's own)` (RC19d) or `(... through MMH5.5 RC19k's 55u.dll, the same for a script)` (RC19k).

**The default** ("MMH5.5's file" in the panel, and what the host sends when it chose nothing) is what this PC's MMH5.5 does by itself: the 6 bytes at `0x00992d2a`, read in the lobby (55u.dll changed them at start-up). The original `0f 84 4e 01 00 00` (the original game, RC19d) = off; anything else (RC19k: `90 90 90 90 90 90`) = on. Logged once: `rules: map scripts: the game's "no map script" jump (0x00992d2a) is 90 90 90 90 90 90: changed (MMH5.5 RC19k: ...)`. The panel shows it as "MMH5.5 alone: On/Off" when the host changed it.

**The protocol** is now version 3 (18 rules, after step 2's version 2): a PC with an older version says hello with it, the host treats it as a PC without the rules, and nobody gets the host's rules (as before for a PC without the add-on).

### Research: where the class table lives (question 1)

- **`HeroClass.xdb` is read once, at start-up.** The exe's static initialisers (`0x00dd2d15` → `0x00ae2980`) make the table's holder (0x34 bytes, vtable `0x00e788fc`, with the type name `STable_HeroClassDesc_HeroClass`, the path `/GameMechanics/RefTables/HeroClass.xdb`, the global `0x01024c54` and the table's size: `push 9` at `0x00ae29df`, 74 in MMH5.5's exe) and register it (`0x00ccc110`, list `0x010dbd7c`). The start-up's database step `0x00836b80` (fonts, crag info, then the tables) calls `0x00cccd60(0)`, which loads every registered table (holder slot `0x1c`); with an argument it reloads only the tables whose files changed (an editor feature). Our log has the table in memory in the waiting room, before any map. **So serving another file per game cannot work**: the add-on edits the table in memory.
- **The table in memory:** class *c* is at `[0x01024c54] + 8 + c × 0x44` (`0x00ad5af0`). There: `+4` the name text, `+0x10` **SkillsProbs**, a vector (begin, end, capacity) of 12-byte items: a word (the same in every item), the skill (`+4`), the chance (`+8`); `+0x20..+0x2c` the attribute chances (offence, defence, spellpower, knowledge: `0x00b50a50`); `+0x30` the preferred spells (the AI's spell shop, `0x004e6d30`). MMH5.5 (RC19d and RC19k): 24 classes with a list of 12, each adding up to 100, the 24 skills of the union below (74 places, the others empty). The class numbers (matched from the logged lists): 1 Knight, 2 Ranger, 3 Wizard, 4 Demon Lord, 5 Necromancer, 6 Warlock, 7 Runemage, 8 Barbarian (vanilla's 8 first), then 9 Heretic, 10 RangerA, 11 Warden, 12 Enchanter, 13 Sorcerer (the Warlock's list), 14 FlamekeeperA, 15 Reaver, 16 NecromancerA, 17 WarlockB, 18 Beastmaster, 19 Guildmaster, 20 Seer, 21 WizardA, 22 Elementalist, 23 RunemageA, 24 Shaman. (MMH5.5 reuses the names across factions: its Knight, Ranger and Heretic are Haven's, its Necromancer, RunemageA and FlamekeeperA Fortress's, and so on: [lobby-audio-classes.md](lobby-audio-classes.md) item 4.)
- **Who reads the chances:** only `0x00875ba0` (`__fastcall(skill, class)`: the item's chance, 0 when the class does not list the skill), called once, by the level-up's new-skill weights (`0x00b50be0`). The class's other readers use the name (`0x00b4d640`, `0x005b8510`: interface) and the preferred spells (the AI).

### Research: the level-up's offer (question 2)

`0x00b52810` ("== Start choosing skills for level-up ==" in the game's debug log, when its log flag is on) builds the offer: "Skill 1: new skill" (`0x00b50db0`, else an upgrade `0x00b4f400`), "Skill 2" (an upgrade, or a new skill without the first one), "Perk 1: standart perk" and "Perk 2: special perk" (`0x00b4f5c0`, from the hero's own list of learnable perks, its vtable slot `0x188`). The new skill (`0x00b50db0`, `__thiscall(hero, excluded skill)`, the hero's class at `+0xa4`):
1. none when the hero has more than 5 skills (MMH5.5's `55u.dll` changes that compare at `0x00b50de5`: 8 slots);
2. the candidates: every skill of the skill table without a type or class mark (`0x00875e20`: the major skills; in MMH5.5 all 27 have class "none", see below), plus the class's vanilla faction skill (`0x00875550`: classes 1..8 → Training, Avenger, Artificier, Gating, Necromancy, Invocation, Runelore, Demonic Rage; in MMH5.5 that skill is then in the list twice, so it weighs double: the game's own behaviour, kept), minus the hero's skills and the excluded one;
3. the weights: the class table's chance of each candidate (`0x00875ba0`); a skill not on the list weighs 0;
4. the draw: `0x00b509b0` sums the weights and takes **one random number in [0, sum − 1]** from `0x00b4f2f0` (the generator at `+0x1a0` of the level-up's owner, the world's shared one, which the game's `log_random_calls` traces), then the first candidate whose running sum passes it.

**So:** changing the table changes the offers (a skill with a chance > 0 can be drawn), the number of random numbers drawn does not change (one per new skill), and every PC with the same table draws the same skill from the same shared numbers. The robot runs below show it (and the checksums stay equal).

### Research: what still limits skills (question 3)

- **`Skills.xdb`:** MMH5.5's 27 major skills (`SKILLTYPE_SKILL`) all have `HeroClass` "none" (vanilla ties its 8 faction skills to their class: Training to the Knight...). Nothing there keeps a class from a major skill; the class table alone did. MMH5.5's classes already mix factions' skills (Necromancy on 6 classes of 4 factions).
- **Skills no class lists:** Barbarian Learning (183) and Voice (187), vanilla's Barbarian skills. MMH5.5 never offers them; "Unlocked" adds only the skills some class lists (24), so they stay out.
- **The "Shatter" skills:** separate major skills (Shatter Destructive 191, Dark 195, Light 199, Summoning 203). MMH5.5 gives "might" classes Shatter X instead of X (its Knight: Shatter Light, Destructive, Summoning, and Dark Magic). Nothing in the engine (the new-skill code above, the one `55u.dll` spot there) or in the scripts makes them exclusive: unlocked, a hero can hold both Light Magic and Shatter Light Magic. Not changed (MMH5.5's design).
- **Perks (abilities):** each perk offer comes from the hero's list of learnable perks (`0x00b4f5c0` → hero slot `0x188`). MMH5.5's `Skills.xdb` gives 116 special perks per-class requirements (`SkillPrerequisites`: class + the perks needed), naming only the classes MMH5.5 meant to have them (Guardian Angel: 5 classes). **Not checked:** what that list does for a class it does not name (no extra requirement, or no perk). So a skill newly offered to a class may come with fewer (or other) special perks than for MMH5.5's own classes; the standard perks (no per-class list) are not affected. To check with a trace of the perk offers in a long game.
- **Witch huts:** MMH5.5's scripts (`H55_WitchVisit` in `H55-AdvMap.lua`) offer the hut's skill from MMH5.5's own per-class lists (`H55_WitchSelect` in `H55-Tables.lua`, the class from `H55_GetHeroClass`'s per-hero lists in `H55-Core.lua`). They keep MMH5.5's lists.
- **The skill wheel:** MMH5.5's pages (`MMH55-Skillwheel.pak`, the hero screen's round button) show each class's own tree. Hiding them is [mmh55-vs-vanilla.md](mmh55-vs-vanilla.md) C.2 #16 (not built).
- **Scripts that give skills** (`GiveHeroSkill`: quests, the governors...) are MMH5.5's, unchanged.

### Saves (question 4)

**A game started unlocked stays unlocked when it is loaded, on every PC with the add-on.** The table is not part of a save (it is reference data), and a multiplayer load does not go through the start message or `CRunMPGame` (see `map_scripts`, "Saves"). So the rule travels **in the save itself**: the world's own serializer (`NWorld::CWorld`'s `CObjectBase` vtable `0x00e625d8`, slot 3 `0x009a2340`: `sub ecx,[ecx-4]; jmp 0x009a2350`, checked) writes the world's chunks 1 to `0x3e`; our wrap adds chunk **`0x4f`** (64 bytes: `OHW1;class_skills=1;class_chance=2`) after them while this game's class skills are unlocked, and nothing otherwise (a save of a locked game is byte for byte the game's). When a world is **read** (a load), the wrap reads chunk `0x4f` (the game's reader zero-fills a missing chunk) and sets the table from it: unlocked, or MMH5.5's lock for a save without it. Each PC loads its own copy of the save (the same world), so every PC gets the same table.

- A PC **without the add-on** skips the chunk (the reader looks chunks up by number) and loads the save on MMH5.5's lock. In a multiplayer load with such a player the PCs would then differ from the first level-up: as for a new game, every player needs the add-on. Not guarded (the load's lobby was not studied).
- **How the player notices:** the in-game panel (F2) shows the class skills as the table is (with "The class skills come from the loaded save" after a load), and the log has `rules: class skills: a saved game is read: its rules` then `UNLOCKED`.
- **Only the game's file saver gets the chunk.** The world's serializer is also run by three other savers (robot census): `CWorldCRCSaver` (`0x00e93664`, the multiplayer checksums), `CChunklessSerializer` (`0x00e8d7bc`) and `CPointerSearchSerializer` (`0x00e512b4`). The wrap calls the game's serializer, compares the saver's vtable with `CStructureSaver`'s (`0x00e93dfc`: saves, loads) and does nothing else for the others: they see the world exactly as without the add-on. **Why so strict:** a first version also asked every saver whether it was reading (its slot 15, harmless on all four) and took a lock; with it, three of three RC19k LAN runs of 12 AI turns had a few pairs of different world checksums (`20261102-012505`, `-013519`, `-015203`; then equal again), **even with the rule off**, while main's build (`-014756`), the released 0.2.6 (`-013059`), the same build without the wrap (`-015801`) and the strict wrap (`-020359`) were all in step. The cause was not pinned (the work done on those calls has no effect we could find; a leftover on the stack read by the game later is one guess); the strict wrap leaves the checksum paths as the game has them.
- A new game's start always decides (`CRunMPGame` and `CStartSingleAdventureMap` are new games only: a load goes through neither, the robot's single-player load below and `map_scripts`' "Saves"). A lobby within 60 s after a save was read does not undo the save's rule (a multiplayer game being loaded while its lobby may still run).

## Findings worth knowing

- **MMH5.5's scripts in multiplayer need a map script** (with RC19d). A random map straight from the game's generator has `<MapScript/>` (empty) in its `map.xdb`; in a multiplayer game no `advmap-startup.lua` runs for it, so none of MMH5.5's script features run there (governors, conversion, town gate, mine guards, mixed stacks, the AI bonus, the random map extras, the Savage/Nightmare modes' script part). In single player they do run on the same map. MMH5.5's Mapmixer (and the map editor) save random maps with a script; the owner's saved maps (`MAP_JoacJoz`, `6P-epic-...`, `TEAMJOACJOZ`...) have one, while `MMH55_RMG_Map_002` / `_007` and the robot's rebuilt copies do not. RC19k runs them anyway; the rule `map_scripts` now decides ([above](#mmh55s-scripts-on-random-maps-map_scripts-2026-11-01)).
- **One RC19k LAN run desynced at once and the same run again did not** (robot `20261101-221540-lan`: RC19k's own way, no host's rules, `MMH55_RMG_Map_002`: 299 of 300 world checksums different from the first one; `20261101-224512-lan`, the same set-up: 228 equal). The same map was in step under RC19k with no scripts and with our empty script, and RC19k's own way was in step on a map made by RC19k. Cause not found. Something to watch in the group's first RC19k games on generated maps (the co-op guard reports a desync).
- The scripts open `H55-Settings.lua` once per map start, on every PC, about 0.3 s after the world starts (after `advmap-startup.lua`, `events.lua`, `advmap-common.lua`, `common.lua`, `H55-Tables.lua`, `H55-Core.lua`, `H55-Library.lua`).
- With one client, the host serializes `CMPStart` three times (the console has "SendDirect: command: class NMP::CMPStart" to PC 0, the host itself, and to PC 1; the third is probably a size or checksum pass): each carries the chunk. The host's game does not read its own copy back (no "the host's start message" line in its log).
